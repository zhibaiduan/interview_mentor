## 0. 文档导读

本文档是面向开发落地的执行型 PRD，不是概念文档。每一个模块都包含：功能定义、验收标准、优先级（P0/P1/P2）和 MVP 边界说明。

**关键约束**
- 团队规模：1 人独立开发
- 可用时间：约 12 天（截止 6 月 20 日）
- 核心目标：跑通完整核心流程，可 demo，可招募 seed user
- 技术方向：Next.js 14 + Tailwind + Supabase + DeepSeek API（详见技术架构文档）

**MVP 核心假设（需要通过 demo 验证）**
> 非母语技术求职者，是否愿意使用一个基于自己简历和 JD 生成个性化问题、并给出双视角反馈的工具？

## 1. 产品全景：功能模块地图

```
Interview Mentor  （10 个模块，4 层结构）
│
├── 入口层
│   ├── [P0] M1 · Landing Page       ← 价值传递，新用户转化
│   ├── [P0] M2 · 认证               ← 登录/注册，头像下拉含退出
│   └── [P1] M9 · 个人主页           ← 复访驱动，训练记录，资产管理
│
├── 核心流程层
│   ├── [P0] M3 · 面试前设置         ← 简历、岗位、模式、题型、追问强度
│   ├── [P0] M4a · 专项练习 Mode 1   ← 单轮，题型专项，问题链
│   ├── [占位] M4b · 全流程 Mode 2   ← 即将开放，UI 占位
│   ├── [P0] M5 · 模拟面试会话       ← 来电动画，沉浸式问答（共用引擎）
│   └── [P0] M6 · 面试反馈           ← 全局+单题，面试官视角+Mentor视角
│
├── 资产层
│   ├── [占位] M7 · Answer Polish    ← 即将开放，数据结构预留
│   ├── [P1] M8 · 我的答案库         ← 保存、编辑、分组搜索
│   └── [P1] M10 · 题库              ← 公共分类题目，AI 抽题参考
│
└── 账户层（合并入 M9，无独立页面）
```

**MVP 必须跑通的最短路径（P0 链路）：**
```
Landing Page → 登录验证 → 面试前设置 → 专项练习 → 模拟面试会话 → 反馈页面
```

## 2. 用户旅程（完整版）

### 2.1 首次用户旅程

```
[1] 访问 Landing Page
    ↓
[2] 点击「开始模拟面试」
    ↓ 触发登录检查
[3a] 未登录 → 跳转登录/注册页 → 完成后返回
[3b] 已登录 → 直接进入
    ↓
[4] 面试前设置页
    ├── 上传/粘贴简历
    ├── 输入目标岗位信息（粘贴 LinkedIn JD 或手动填写）
    └── 选择训练模式
        ├── Mode 1：专项练习（可选题型：行为题 / 简历问题 / HR 动机）
        └── Mode 2：全流程模拟（显示「即将开放」，不可点击）
    ↓
[5] 确认开始 → 进入「来电」过渡动画
    ↓
[6] 沉浸式面试会话页
    ├── AI 面试官自我介绍
    ├── 基于简历和 JD 逐题提问（默认固定 3 道主问题）
    └── 用户回答（MVP 支持文字；语音录入作为 P1）
    ↓
[7] 面试结束（主动触发 or 用户退出）
    ↓
[8] 反馈页面
    ├── 全局反馈：HR 视角评分 + Mentor 成长建议
    └── 单题反馈：每题 HR 评估 + 「Answer Polish」（即将开放）+ 保存到 Answer Bank
    ↓
[9] 结束 → 跳转个人主页 / 历史记录
```

### 2.2 回访用户旅程

```
[1] 直接登录 → 个人主页
[2] 查看历史面试记录
[3] 复用已保存的简历 → 快速进入新一轮练习
[4] 查看 Answer Bank 中保存的答案
```

## 3. 功能模块详细定义

---

### 3.1 Landing Page

**目的**：传达产品价值主张，引导用户开始，验证登录状态。

**P0 功能：**
- 产品 Headline + 一句话定位（直接用 Brief 里的定位）
- CTA 按钮：「开始模拟面试」
- 登录状态检查：
  - 已登录 → 直接进入面试前设置
  - 未登录 → 跳转登录页，完成后 redirect 回来
- 产品核心价值简介（3 个要点，可以是 icon + 文字）

**P1 功能：**
- 用户评价 / 社交证明（demo 阶段可用虚构内容占位）
- FAQ 简版

**验收标准：**
- [ ] 未登录用户点击 CTA → 跳转登录页，登录后自动回到原流程
- [ ] 已登录用户点击 CTA → 直接进入设置页，无需再次确认
- [ ] 页面在移动端可正常浏览（不要求完美，能用即可）

---

### 3.2 认证模块（登录/注册）

**P0 功能：**
- Email + 密码注册/登录
- Google OAuth（P0，减少用户摩擦）
- 登录后 redirect 到原来的目标页面

**P2 功能（本期不做）：**
- 忘记密码
- 邮件验证
- 第三方 OAuth（GitHub 等）

**技术建议：** 统一使用 Supabase Auth，不使用 NextAuth，不自己实现认证。

**验收标准：**
- [ ] 用户可以用 Email 完成注册和登录
- [ ] 用户可以用 Google OAuth 完成登录/注册
- [ ] 登录后 session 持久化（刷新页面不退出）
- [ ] 未登录访问需要登录的页面 → 自动跳转登录页

---

### 3.3 面试前设置页

**目的：** 收集生成个性化问题所需的三个核心输入：简历、JD、训练模式。

**P0 功能：**

**Step 1 — 简历信息**
- 文本框粘贴简历内容（MVP 优先，不要求 PDF 解析）
- 如果个人主页已有保存的简历 → 提供「使用已保存简历」快捷选项
- 字数提示（建议 200–2000 字）

**Step 2 — 目标岗位信息**
- 文本框粘贴 JD 内容（LinkedIn / Stepstone 等）
- 或手动填写：公司名、岗位名、核心要求（3 个字段）
- 二选一，不强制两个都填

**Step 3 — 训练模式选择**
- Mode 1：专项练习（可选择）
  - 子类型选择：行为题（Behavioral）/ 简历深挖（Resume-based）/ HR 动机题（Motivation）
  - 题目数量：3 题 / 5 题（用户可选）
- Mode 2：全流程模拟
  - 显示为灰色卡片，标注「即将开放」
  - 点击后显示 tooltip：「全流程模拟正在开发中，即将上线」
  - 不可进入

**P1 功能：**
- 简历上传（PDF → 后端解析为文本）
- 保存当前设置为「模板」供下次复用

**验收标准：**
- [ ] 简历和岗位信息至少填写一项才能继续（不能空提交）
- [ ] 选择 Mode 2 时无法继续，显示「即将开放」提示
- [ ] 确认后，设置信息传入 AI 问题生成模块

---

### 3.4 模拟面试会话（核心模块）

**目的：** 提供沉浸式、个性化的模拟面试体验。这是整个产品的核心价值环节。

#### 3.4.1 进入过渡动画

**P0：**
- 「来电」动画效果（模拟手机来电界面）
- 显示「[公司名] 正在呼叫...」
- 用户点击「接听」进入面试会话

**目的：** 创造仪式感，帮助用户进入「面试状态」，降低后续紧张感。

#### 3.4.2 面试会话界面

**P0 功能：**

**界面布局：**
- 简洁沉浸式设计，去除干扰元素
- 显示：当前问题编号（1/5）、AI 面试官「发言」区域、用户回答区域
- 底部操作栏：回答输入 + 提交 + 退出按钮

**AI 面试官行为：**
- 开场白：AI 自我介绍（「你好，我是 [公司] 的 HR，今天我们做一个 [X] 分钟的专项练习...」）
- 逐题提问，每题一屏，不一次性展示所有问题
- 根据用户回答触发 0–5 个追问（基于回答质量动态判断，不强制追问）
- 问题个性化：基于用户简历和 JD 生成，不使用通用题库

**回答方式（MVP 关键技术决策，见第 5 节）：**
- 方案 A（推荐 MVP）：文字输入 + 语音输入二选一
  - 用户可以打字回答，也可以点击录音
  - 录音完成后转文字显示，用户可编辑后提交
- 方案 B：纯文字输入（最低成本，体验最弱）
- 方案 C：实时语音流（最佳体验，成本最高，建议 V2）

**会话结束：**
- 自然结束：AI 在最后一题后说「感谢参与，我们稍后给你反馈」
- 用户主动退出：点击「结束面试」→ 确认弹窗 → 跳转反馈页

**P1 功能：**
- 面试计时器（倒计时或正计时）
- 问题可「跳过」（跳过的问题在反馈页标注）

**P2 功能（不做）：**
- 实时语音流（Voice streaming）
- 视频录制
- 表情/肢体语言分析

**验收标准：**
- [ ] 开场白正确使用用户输入的公司名和岗位名
- [ ] 至少 3 道问题基于用户简历中的具体项目/经历生成（不是通用题）
- [ ] 用户提交回答后，AI 能基于该回答生成追问（至少 1 次）
- [ ] 用户点击「结束面试」→ 有确认弹窗 → 确认后跳转反馈页
- [ ] 所有回答内容被保存，进入反馈生成流程

### 3.5 反馈页面

**目的：** 这是产品最核心的差异化页面，也是验证核心假设的关键。用户在这里感受到「这个工具真的懂我的简历和这个岗位」。产品价值最终落在**「你以为自己表达了什么」vs「招聘官实际听到了什么」**这个对比上，而不是评分数字。

#### 3.5.1 单题反馈区（核心，优先设计）

每道题的反馈采用**三段式强对比结构**，这是产品产生 aha moment 的核心模块：

```
┌─────────────────────────────────────────────┐
│  Q1: Walk me through your X project...       │
│  你的回答：[完整回答文字]                      │
├─────────────────────────────────────────────┤
│  📡 Your Answer Signal                       │
│  你实际传递的信号（你以为说了什么）             │
│  → 提到了项目背景，使用了"we"而非"I"           │
├─────────────────────────────────────────────┤
│  👂 Interviewer Heard                        │
│  招聘官实际听到了什么                          │
│  → 团队成员，ownership 不清晰，缺少个人决策证明  │
├─────────────────────────────────────────────┤
│  ✦ Next Version Should Include               │
│  下一版回答应该加入什么                        │
│  → 用"I led..."开头，加入一个具体决策和结果数字  │
└─────────────────────────────────────────────┘
```

**P0 功能（每道题）：**
- 显示：原问题 + 用户完整回答（含追问链路）
- **Your Answer Signal**：你实际传递的信号，基于回答内容客观描述
- **Interviewer Heard**：面试官实际听到了什么，指出感知偏差
- **Next Version Should Include**：1–2 条具体可执行的改进，不是泛泛建议
- 「保存到答案库」按钮 → 保存成功 toast（P0），完整答案库列表 P1

**三段式案例：**

用户回答：
> We built a dashboard for the operations team. I helped define some metrics and worked with engineering. It made the process more efficient.

Your Answer Signal：
> 你传递出的信号是：参与过一个 dashboard 项目，理解指标定义，也有跨职能协作经验。但回答主要使用 "we"，个人职责边界不清晰，结果只说了 "more efficient"，没有证明影响力。

Interviewer Heard：
> 面试官听到的是：这是一个团队项目，候选人可能参与了需求整理，但暂时看不出是否拥有 ownership，也听不到具体决策、trade-off 或量化结果。因此会担心你是在执行，而不是主导。

Next Version Should Include：
> 下一版回答应加入三件事：1）用 "I led the metric definition..." 明确你的个人职责；2）说出一个你做过的关键取舍，例如为什么选择 activation rate 而不是 page views；3）补一个结果数字，例如 "reduced weekly reporting time by 30%"。

**P1 功能（每道题）：**
- Answer Polish 按钮（灰色占位，点击提示「即将开放」）
- 缺失信号标签：ownership / impact / decision / language 等可视化标签

#### 3.5.2 全局反馈区

**P0 功能：**

**面试官视角（评估类）：**
- 整体印象（2–3 句话，不是评分数字）
- 最突出的正面信号（1 个，具体）
- 最大的负面信号 / 顾虑（1 个，具体）
- 是否会推进下一轮（would_advance: yes / maybe / no）

> 评分数字作为辅助信息显示，不作为主信息。雷达图降为 P1。

**Mentor 视角（成长类）：**
- 当前最大短板（1 个，具体到行为）
- 最优先的改进动作（具体可执行，如「下次用 I led 替代 we built」）
- 下一步练习方向推荐

**验收标准：**
- [ ] 每道题三段式结构（Signal / Heard / Next Version）完整展示
- [ ] Interviewer Heard 明确指出感知偏差，而非重复用户的话
- [ ] Next Version 建议具体到行为级别，不出现「更具体」「更自信」等无效建议
- [ ] 保存按钮 → 成功 toast，数据写入数据库
- [ ] Answer Polish 按钮显示「即将开放」，不报错
- [ ] 全局面试官视角包含 would_advance 判断
- [ ] Mentor 建议包含至少 1 个可立即执行的动作

### 3.6 我的答案库（Answer Bank）

**目的：** 用户主动打磨和积累的个人答案资产库，产品留存的核心钩子。

**定位说明：**
答案库不是自动归档的练习日志，而是用户**主动认可并保存**的答案集合。每条记录保存三层答案，职责分离：

| 字段 | 含义 | 是否只读 |
|------|------|---------|
| `original_answer` | 面试时的原始回答，永不修改 | ✅ 只读 |
| `polished_answer` | AI Polish 后的版本，Answer Polish 开放后才有值 | ✅ 只读 |
| `saved_answer` | 用户在答案库里维护的「最终版」，可自由编辑 | ❌ 可编辑 |

`saved_answer` 的操作逻辑：
- 保存时默认 = `original_answer`
- Answer Polish 开放后，用户可一键「采用 Polish 版本」→ `saved_answer` 更新
- 用户也可以直接手动编辑 `saved_answer`
- `original_answer` 永远作为对照参考，不受影响

**P0 功能（MVP 范围）：**
- 从反馈页「保存到答案库」→ 创建记录，显示成功 toast
- `saved_answer` 初始化为 `original_answer`
- 答案库列表页基础版本：按题型分组展示已保存答案
- 点击单条 → 展开查看完整问题 + 三层答案
- 编辑 `saved_answer`：纯文本编辑，保存更新

**P1 功能：**
- 搜索：按关键词搜索问题文本
- 删除记录
- 添加个人备注（`note` 字段）
- Answer Polish 开放后：显示「采用 Polish 版本」按钮

**P2 功能：**
- 导出为 PDF
- 按岗位 / 公司筛选

**验收标准：**
- [ ] 从反馈页保存 → 显示成功 toast，数据写入数据库
- [ ] `saved_answer` = `original_answer`（初始值正确）
- [ ] P1：列表按题型分组正确
- [ ] P1：编辑 `saved_answer` 后保存 → 刷新页面内容不丢失
- [ ] P1：`original_answer` 始终显示面试时的原始内容，不随编辑变化

### 3.7 个人主页（M9）

**目的：** 复访驱动——用户每次进来立刻知道「下一步做什么」，一键进入练习。同时管理个人资产（简历、JD 历史、训练记录）。账户操作（退出登录、邮箱显示）合并入右上角头像下拉菜单，无独立账户页。

**页面布局：两个区域**

**区域一：复访驱动区（页面上半部分）**
- 欢迎语 + 用户名
- 「开始新的练习」CTA 按钮 → 跳转面试前设置页
- 上次练习概要卡片：日期、岗位、整体评分、「查看反馈」快捷入口
- 轻量进度提示：「你已完成 X 次练习」（纯文字，不做图表）

**区域二：资产管理区（页面下半部分）**
- 我的简历：已保存简历列表，可删除，可点击进入设置页时自动填入
- JD 历史：最近使用过的 JD，可快速复用
- 答案库入口：跳转 M8 答案库页
- 题库入口：跳转 M10 题库页

**右上角头像下拉菜单（账户操作）：**
- 显示登录邮箱
- 退出登录
- 修改密码（P1）

**P0 功能：**
- 复访驱动区完整展示
- 历史面试记录列表（最近 5 条，「查看更多」展开全部）
- 简历管理（查看 + 删除）

**P1 功能：**
- JD 历史管理
- 练习次数统计

**验收标准：**
- [ ] 「开始新的练习」CTA 跳转设置页
- [ ] 历史记录按时间倒序，显示关键信息
- [ ] 点击历史记录 → 进入对应反馈页（只读）
- [ ] 已保存简历可在设置页直接调用
- [ ] 头像下拉显示邮箱 + 退出登录功能正常

| 模块 | 功能 | 优先级 | Demo 必须 | 说明 |

### 5.3 Answer Bank 三层字段说明

每条记录包含三个答案字段，职责严格分离：

| 字段 | 含义 | 可否编辑 |

| `original_answer` | 面试原始回答，永久只读 | ❌ |
| `polished_answer` | AI Polish 版本，Answer Polish 开放后才有值 | ❌ |
| `saved_answer` | 用户维护的最终版，可自由编辑 | ✅ |

### 5.4 单次面试成本估算

- 纯文字模式：约 $0.002 / 次
- 含语音（Whisper）：约 $0.032 / 次
- 100 次 seed user 测试：$3–5，完全可控

## 6. 关键技术风险与应对

| 风险 | 影响 | 应对方案 |
|------|------|---------|
| AI 输出不稳定（乱格式、遗漏字段） | 高 | 所有步骤强制 JSON schema 输出 + 后端 validation |
| 追问质量差（追问变成重复问题） | 中 | 在追问 prompt 中明确禁止重复，给 3–5 个好追问示例 |
| Whisper 识别非英语效果不稳定 | 中 | 支持文字输入兜底；指定 language 参数给 Whisper |
| Demo 时 API 超时或失败 | 高 | 准备 fallback 静态数据（hardcode 一套完整的 demo 数据） |
| 成本超支 | 低 | MVP 统一 DeepSeek V3；seed user 限制每天次数 |
| 反馈没有 aha moment | 高 | 准备 5 个 golden cases，持续评估 Signal / Heard / Next Version 是否具体、尖锐、可执行 |
| 时间不足 | 高 | 严格按 P0 清单执行，P1 全部砍掉，Demo 后再补 |

## 8. 产品设计指导原则

这是所有页面和功能决策的参照系。每次做设计决策时，先对照这三条原则过一遍。

---

### 原则一：简单是第一竞争力

> 用户在面试压力下来使用这个产品。任何增加认知负担的设计都是在给用户添麻烦。

**含义：**
- 每个页面只有一个主要动作。设置页的主动作是「开始面试」，反馈页的主动作是「理解反馈」，不在同一页面竞争注意力
- 选项越少越好。追问强度三档已经是上限，不要继续细分
- 信息层级最多三层。能用一句话说清楚的，不用段落；能用段落说清楚的，不用页面
- 默认值做好选择。用户不应该在设置页花超过 2 分钟

**对开发的指导：**
- 新增功能时，先问「如果不做这个，用户有没有其他办法」——有就不做
- UI 上出现超过 3 个并列选项时，重新考虑信息架构
- 页面加载时，用户应该在 3 秒内知道「我现在该做什么」

---

### 原则二：信息价值突出

> 这个产品的核心价值是「让用户看到自己看不到的东西」。反馈必须让用户有「原来如此」的顿悟感，而不是「我已经知道了」的无聊感。

**含义：**
- 反馈的最高标准是「具体到让人有点尴尬」——用户看到后会想「我确实是这样的」
- 每一条反馈都必须指向具体的、可改变的行为，而不是评分和标签
- 「招聘官实际听到了什么」永远比「你的回答得了 3 分」更有价值
- 对比结构（原始 vs 改进）比单向陈述更有说服力

**对开发的指导：**
- AI prompt 的 negative example 比 positive example 更重要——「不要说『很好但可以更具体』」必须写进每个 Agent 的 prompt
- 反馈页的信息密度可以高于其他页面，但层级必须清晰：全局 → 单题 → 具体改进
- 评分数字（1–5 分）永远是辅助信息，不是主信息；文字反馈才是主信息

---

### 原则三：操作链路突出

> 用户每次进来都应该能快速找到「下一步做什么」，不应该迷失在功能之间。

**含义：**
- 每个终态页面（反馈页、答案库）都有明确的「下一步」出口
- 用户完成一次面试后，回到主页看到的第一件事是「开始新的练习」CTA，而不是数据统计
- 核心流程（设置 → 面试 → 反馈 → 保存）是一条高速公路，其他功能是匝道，不是路障
- 「即将开放」的功能不应该挡在主路上，只能作为路边的指示牌

**对开发的指导：**
- 每个页面在设计时，先画出「用户从哪里来」和「用户去哪里」，两个方向的出口都要明确
- 反馈页底部：「保存到答案库」和「开始新练习」是并列的主要 CTA
- 答案库和题库之间没有强制路径，用户可以从任何入口进来，也可以从任何入口出去

---

### 原则 0（元原则）：先让它工作，再让它好看，再让它快

MVP 阶段的优先级顺序：**功能正确 > 体验流畅 > 视觉精致 > 性能优化**。

但这不意味着视觉可以随意——Landing Page 和反馈页是产品的「门面」，这两个页面的视觉质量直接影响用户是否愿意继续。其他页面可以简洁，但不能粗糙。
